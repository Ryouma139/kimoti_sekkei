# きもちとコード 仕様書

学習日記ブログ「きもちとコード」の仕組み・画面ごとの表示条件・管理画面・公開方法をまとめたものです。
コンポーネント（部品）ごとの props や書き方は [components.md](components.md) を見てください。

- 公開URL: https://ryouma139.github.io/kimoti_sekkei/
- 管理画面: https://ryouma139.github.io/kimoti_sekkei/admin/
- リポジトリ: https://github.com/Ryouma139/kimoti_sekkei （公開リポジトリ・`main` ブランチ）

---

## 1. 全体の仕組み

```
記事（Markdown ファイル）── src/content/feel・tech・learn
   │  手元で書いて push ／ 管理画面で保存（GitHub に直接コミット）
   ▼
GitHub（main ブランチ）
   │  push・毎日 0:00（日本時間）・手動 で GitHub Actions が動く
   ▼
ビルド（astro check && astro build）
   │  記事を全部読み、集計（カレンダー・学習時間・連続日数など）して HTML を作る
   ▼
GitHub Pages で公開（静的サイト）
```

- **DB は使いません。** 記事はリポジトリ内の Markdown が正です（[markdown-over-cms.md](../src/content/tech/markdown-over-cms.md) の方針）。
- 集計はすべて**ビルド時**に行います。サイトを見る人のたびに計算することはありません。
- 「今日」は**ビルドした日（日本時間）**です。そのため毎日 0:00 に自動でビルドし直しています。

### DB を使わない理由

| 観点 | 内容 |
|---|---|
| 必要性 | 書くのは1人・記事は1日数件・全員に同じページを出すだけで、DB の強み（同時書き込み・大量検索・人ごとの表示）を使わない |
| 運用 | 静的サイトなら無料・保守ほぼ不要。DB を使うとサーバー・料金・障害対応が増える |
| 安全 | 公開しているのは HTML だけなので、攻撃される場所がほとんどない |
| 履歴 | 記事がファイルなので Git の差分で書き直しの履歴が残り、手元にもバックアップがある |

コメント・いいね・複数人の執筆などが必要になったら、その部分だけ外部サービスを足す形を検討します。

## 3. 記事データの仕様

### 3.1 項目（`src/content.config.ts`）

**共通**

| 項目 | 必須 | 内容 |
|---|---|---|
| `title` | ○ | タイトル |
| `date` | ○ | 日付（`2026-10-04`）。カレンダー・並び順の基準 |
| `created` | | 書いた日時（`"2026-10-04T21:30:15+09:00"`）。**管理画面で保存すると自動で入る**。同じ日付の並び順に使う |
| `tags` | | タグの配列。省略時 `[]` |
| `draft` | | `true` にすると**サイトのどこにも出ない**（下書き）。省略時 `false` |

**きもち日記（feel）**：`mood`（必須：`great` / `happy` / `calm` / `meh` / `down`）、`weather`（任意）

**まなびログ（learn）**：`minutes`（必須：1以上の整数・分）、`category`（必須：`categories.ts` のどれか）、`project`（任意：テックノートの id）、`source`（任意：URL）

**テックノート（tech）**：`type`（必須：`project` / `note`）、`updated`（任意：更新日）、`summary`（任意）
- `type: project` のときだけ使う項目：`icon`（3文字まで）、`status`（`plan` / `run` / `done`）、`progress`（0〜100）、`stack`（配列）、`repo`（URL）

項目の決まりに合わない記事があると**ビルドが失敗し、公開されません**（GitHub の Actions タブにエラーが出ます）。

### 3.2 ファイル名・id（スラッグ）

**ファイル名（拡張子なし）が記事の id（スラッグ）になり、URL に使われます。** Astro が読み込むときに作り、英字は小文字になります。

| 種類 | 管理画面で作るファイル名 | URL |
|---|---|---|
| feel | `2026-10-04.md`（**1日1件**） | `/feel/2026-10-04/` |
| learn | `2026-10-04_iam-policy.md`（日付_スラッグ） | `/learn/#2026-10-04_iam-policy`（一覧内の位置） |
| tech | `2026-10-04_my-app.md`（作成日_スラッグ） | `/tech/2026-10-04_my-app/` |

- スラッグはタイトルとは別に入力します。使えるのは**英小文字・数字・ハイフン**だけ（例：`iam-policy`）。
- 以前からある記事（`kakeibo-cli.md` など）のファイル名はそのままです。
- id が使われる場所：記事ページの URL、まなびログの `<li id>`、まなびログの `project:`（テックノートの id）、プロジェクトの学習時間の合計。
- **ファイル名を変えると URL が変わり、リンクが切れます。** テックノートの場合は、まなびログの `project:` も直さないと学習時間が 0 になります。

### 3.3 下書き（`draft: true`）

- 記事の読み込みは必ず `getFeel` / `getTech` / `getLearn`（`src/lib/data.ts`）を通り、その中で下書きを除いています。
- 一覧・詳細ページ（ページ自体を作らない）・ホームの統計・カレンダー・タグ・プロジェクトの学習時間・管理画面トップの記事数、すべてに出ません。
- **リポジトリは公開なので、GitHub 上では下書きも誰でも読めます。**
- 公開するときは、GitHub かエディタで `draft` の行を消すか `false` にします（管理画面では既存記事を編集できません）。

### 3.4 並び順（`byDateDesc`）

1. `date` が新しい順
2. 同じ日付なら `created` が新しい順（あとに書いたほうが先）
3. `created` がない記事は、その日の中でいちばん古い扱い
4. `created` がない記事同士はファイル名の順

④まで決めているので、手元（Windows）と GitHub Actions（Linux）でビルドしても並びがずれません。

## 4. 画面と表示条件

URL はすべて `/kimoti_sekkei/` の下です（以下では省略）。

### 4.1 ホーム `/`（`src/pages/index.astro`）

| 部分 | 条件 |
|---|---|
| 最新の気分 | きもち日記の並び順の先頭1件 |
| 累計スタディタイム | まなびログの `minutes` の合計 ÷ 60（時間、切り捨て） |
| 連続学習ストリーク | 学習時間がある日が今日から何日続いているか。今日まだ記録がなければ昨日から数える |
| きもち日記の件数・進行中のプロジェクト数 | 下書きを除いた数／`type: project` かつ `status: run` の数 |
| きもちカレンダー | 今年の1〜12月（下の 4.2） |
| 最近の記録 | 下の表 |

**最近の記録**

1. きもち・まなび・テックから、それぞれ新しい順に **5件ずつ**取り出す（`FEED_SIZE = 5`）
2. まとめて並べ替え：日付が新しい順 → 同じ日なら**きもちを先** → その次は `created` が新しい順
3. 先頭の **5件** を表示

- テックノートの日付は**更新日（`updated`）、なければ作成日**です。
- 行の見た目は `FeedRow`：きもちは顔アイコン、テック・まなびは種類の色の四角＋短い文字（まなび：`50m`＝分、テック：`icon` か タイトルの先頭2文字）。

### 4.2 きもちカレンダー（`src/components/MoodCalendar.astro`）

ホームと年ごとのカレンダーページで使う部品です。

| 項目 | 仕様 |
|---|---|
| 表示する年 | `year` を渡せばその年、なければ今日の年 |
| 月 | 1〜12月を全部 HTML に出し、‹ › ボタンで表示する月を切り替える（JavaScript で `hidden` を付け替え）。1月で ‹、12月で › は押せない |
| 最初に出る月 | 今年なら今月、それ以外の年は1月 |
| 日数 | 月ごとの正しい日数（`daysInMonth`。9月は30日、うるう年の2月は29日） |
| 曜日 | 日曜始まり。1日の曜日に合わせて前に空マスを入れる |
| 気分アイコン | その日のきもち日記の `mood`。同じ日に複数あれば、あとに書いたほう |
| 学習時間バー | その日のまなびログの合計分。**150分で満タン** |
| 今日 | 枠線 |
| 未来の日 | 薄く表示（`opacity: 0.45`）。年に関係なく「今日より後」が対象 |
| 日付をクリック | カレンダーの下に、その日の記録（きもち・まなび・テック）を一覧で表示。記録がない日は「この日の記録はありません」 |

**日付クリックの一覧に載る条件（`itemsByDay`）**

| 種類 | 載る日 |
|---|---|
| きもち・まなび | `date` の日 |
| テック | 作成日（`date`）と更新日（`updated`）の**両方の日**（同じ日なら1回） |

1日の中の並びは、きもち → まなび → テックの順で、それぞれ 3.4 の並び順です。

### 4.3 カレンダー `/calendar/<年>/`（`src/pages/calendar/[year].astro`）

- 左サイドバーの「カレンダー」から開きます（今年のページへ直接リンク）。
- **作られる年**：いちばん古い記事の年 〜（いちばん新しい記事の年と今年の、遅いほう）。年は記事から自動で決まるので、年が変わってもコードの追加は不要です（`calendarYears`）。
- 上部の年ボタンで年を切り替えます。
- 見出しの下に、その年のきもち日記の件数と学習時間の合計を表示します。
- `/calendar/` は今年のページへ移動します（Astro の仕様で約2秒待つため、サイドバーは直接リンク）。

### 4.4 きもち日記 `/feel/`

- 新しい順にカードを並べます。CSS の段組み（`columns`）なので、**左の列を上から下へ → 次の列**の順に並びます。
- 気分のボタンで絞り込めます（並べ替えはせず、他の気分のカードを隠すだけ）。0件なら「この気分の日記はまだありません。」

### 4.5 テックノート `/tech/`

- 「プロジェクト」タブ：`type: project`。並びは **進行中 → 計画中 → 完了**。カードに、そのプロジェクトに紐づくまなびログの学習時間を表示。
- 「考え方メモ」タブ：`type: note`。新しい順。

### 4.6 まなびログ `/learn/`

- 直近7日（今日を含む）の学習時間グラフ（カテゴリ別）
- 今月のカテゴリ別の合計
- TIL 一覧（新しい順）。各項目に `id` があり、`/learn/#<id>` でその位置へ移動できます。

### 4.7 タグ `/tags/<タグ>/`

3種類の記事から、そのタグが付いたものを日付の新しい順に表示します。

## 5. 管理画面

ブラウザのフォームで記事を書き、**GitHub のリポジトリに Markdown を直接コミット**する仕組みです。保存後、自動で公開されます。

### 5.1 画面

| URL | 内容 |
|---|---|
| `/admin/` | **記事を書く**。3種類の入口カード（記事数・最新の日付）と、GitHub トークンの設定 |
| `/admin/posts/` | **保存記事一覧**（下の 5.4） |
| `/admin/feel/` | きもち日記を書く |
| `/admin/learn/` | まなびログを書く |
| `/admin/tech/` | テックノートを書く |

- サイドバーには出していません。`/admin/` を直接開きます。
- 検索エンジンに載せない設定（`noindex`）です。
- 管理画面の各ページの上に「記事を書く／保存記事一覧」の切り替えメニュー（`AdminNav`）があります。フォームでは「記事を書く」が選択中になります。
- 記事フォームでは、トークン未設定なら「保存できません」の警告を出します。
- 「記事を書く」と「保存記事一覧」を開いたとき、**今日のきもち日記がなければポップアップ**（「本日の気持ちが入力されていません。」）を出します（`AdminTodayCheck`）。
  - 「今日」はページを開いた時点のブラウザの日付（日本時間）。ビルド時点の一覧（下書きも含む）になければ、GitHub に `src/content/feel/<今日>.md` があるか確認します（トークンなしでも可）。確認できなかったとき（通信エラーなど）は出しません。
  - 「書く」できもち日記のフォームへ移動。「あとで」を押すと、その日はタブを閉じるまで出しません。
  - 公開ページ（ホームなど）では出しません。

### 5.2 フォームの項目

| 項目 | feel | learn | tech |
|---|---|---|---|
| タイトル | ○ | ○ | ○ |
| 日付 | ○（初期値：今日） | ○（今日） | 作成日○（今日）・更新日 |
| スラッグ | — | ○ | ○ |
| その他 | 気分（顔アイコンから選ぶ・初期値 おだやか）、天気 | 時間（分・初期値30）、カテゴリ、関連プロジェクト、参考URL | 種類（考え方メモ／プロジェクト）、概要。プロジェクトのときだけ：アイコン文字・状態・進捗・技術スタック・リポジトリURL |
| タグ | カンマ（, または 、）区切り | 同左 | 同左 |
| 下書き | ○ | ○ | ○ |
| 本文 | Markdown | Markdown | Markdown（初期値「## 背景／## 決定／## 理由」） |

- カテゴリ・関連プロジェクト・気分の選択肢は、`categories.ts`・テックノートのプロジェクト（ビルド時点）・`moods.ts` から自動で作ります。
- フォームの下に「保存先：<ファイル名>」と「保存される内容を見る」（実際の Markdown）を、入力に合わせて表示します。

### 5.3 保存の流れ（`setupAdminForm`）

```
「保存して公開」を押す（フォームの submit）
  → preventDefault() でブラウザ標準の送信を止める
  → トークンがあるか確認
  → 入力チェック（下の表）
  → GitHub に同じファイル名があるか確認（GET）── あれば保存しない
  → ファイルを作成してコミット（PUT）
  → 「保存しました」＋「コミットを見る」リンク。フォームを空に戻す
  → 1〜2分後、自動デプロイでサイトに反映
```

- コミットメッセージ：`きもち日記: 2026-10-04 <タイトル>` ／ `まなびログ: 2026-10-04 <タイトル>` ／ `テックノート: <タイトル>`
- front matter の文字列は JSON 形式（`"..."`）で書くので、タイトルに `"` や `:` があっても壊れません。
- `created` は保存した時刻（日本時間）が自動で入ります。

**入力チェック**

| 種類 | チェック内容 |
|---|---|
| 共通 | タイトル・日付・本文が空でない |
| feel | **その日のきもち日記がもうないか**（1日1件）。ビルド時点の一覧（下書きを除く）で確認し、まだ反映されていないものは GitHub のファイル名確認で防ぐ |
| learn | スラッグが英小文字・数字・ハイフン／時間が1以上の整数／参考URL が http(s) |
| tech | スラッグ／更新日が作成日より後／（プロジェクト）アイコン3文字まで・進捗0〜100の整数・リポジトリURL が http(s) |
| 全種類 | 同じファイル名がすでにある → 「同じファイル名の記事がすでにあります」 |

**エラーの表示**

| 状況 | メッセージ |
|---|---|
| トークン未設定 | GitHub トークンが設定されていません… |
| トークンが違う・期限切れ（401） | トークンが正しくないか、期限切れです… |
| 書き込み権限がない（401/403） | 書き込む権限がありません… |
| 通信できない | 通信に失敗しました… |

### 5.4 保存記事一覧 `/admin/posts/`

- `src/content` にある記事を、**下書きも含めて**すべて表示します（`getAllForAdmin`。サイトの表示には使わない関数）。並びは 3.4 と同じ。
- 各行：タイトル、種類、下書きの印、日付、ファイルのパス、「サイトで見る」（公開中のみ）、「GitHubで編集」（GitHub の編集画面を新しいタブで開く）。
- 「管理画面で修正」（下の 5.5）と「GitHubで編集」は **GitHub トークンを設定しているときだけ**表示します。未設定なら「記事を書くで設定してください」と案内します。トークンの有無を見るだけで、トークンが正しいかまでは確かめません。また、表示を隠すだけなので、実際に編集できるかは GitHub の権限で決まります（書き込み権限がない人は、編集しても pull request になるだけ）。
- 絞り込み：種類（すべて／きもち／まなび／テック）と状態（すべて／公開中／下書き）を組み合わせられます。並べ替えはせず、合わない行を隠します。
- **一覧はビルドした時点のもの**です。管理画面で保存した直後の記事は、自動デプロイが終わると載ります。
- 閲覧にトークンは不要です（記事はもともと公開リポジトリにあるため）。

### 5.5 管理画面での修正（`?edit=`）

保存記事一覧の「管理画面で修正」を押すと、その種類のフォームが `/admin/feel/?edit=src/content/feel/2026-10-01.md` のように**修正モード**で開きます。

```
フォームを開く
  → GitHub から今のファイルを読み込む（トークン必須）
  → front matter（yaml パッケージで読む）と本文をフォームに入れる
  → 上に「修正中：<ファイル>」の表示、ボタンは「修正を保存」
「修正を保存」
  → GitHub 上のファイルが、読み込んだ時点から変わっていないか確認（sha を比べる）
  → 変わっていなければ同じファイルに上書きしてコミット（メッセージの先頭に「修正」）
```

| 決まり | 内容 |
|---|---|
| 変えられない項目 | 日付・スラッグ（`data-lock-on-edit`）。ファイル名（URL）に使うため |
| `created` | 元の値をそのまま残す。元になければ付けない |
| チェックを省くもの | feel の「1日1件」、learn・tech のスラッグの形式（古い記事のファイル名もそのまま使えるように） |
| 上書き事故の防止 | 読み込んだあとに GitHub 側で変更されていたら保存しない（「ページを読み込み直してから…」） |
| 受け付けるファイル | そのフォームの種類のフォルダ（`src/content/feel/` など）の `.md` だけ |
| 保存後 | フォームはそのまま（続けて直せる）。保存した版を基準に、次の上書き確認をする |

**注意**：front matter は、フォームにある項目だけで作り直します。手で書いたコメント（`# ...`）や、フォームにない項目は修正すると消えます。

### 5.6 できないこと・注意

- **記事の削除と、ファイル名（日付・スラッグ）の変更は管理画面ではできません。** 保存記事一覧の「GitHubで編集」から GitHub の画面で行うか、エディタで行います。
- 保存先は**いつも GitHub** です。`npm run dev` の管理画面で保存しても、**手元のフォルダには入りません**。手元で確認するときは `git pull` してください。
- 管理画面で書いたあとに手元で作業するときも、先に `git pull`（GitHub と食い違うと push で衝突します）。

## 6. GitHub トークン

### 6.1 トークンとは

GitHub のパスワードの代わりに使う「合い鍵」の文字列（`github_pat_...`）です。管理画面から GitHub に保存を頼むとき、GitHub は「書き込みを許された本人か」をトークンで確認します。

| | パスワード | トークン |
|---|---|---|
| できること | アカウントのすべて | 作るときに決めた範囲だけ |
| 期限 | なし | 付けられる |
| 漏れたとき | アカウントごと危ない | そのトークンを消せば終わり |

### 6.2 作り方

1. GitHub → Settings → Developer settings → Personal access tokens → **Fine-grained tokens** → Generate new token
2. Token name（例：`kimochi-admin`）、Expiration（例：90日）
3. Repository access：**Only select repositories → kimoti_sekkei**
4. Permissions → Repository permissions → **Contents: Read and write**（ほかは不要）
5. 表示されたトークンをコピー（**この画面でしか見られない**）
6. `/admin/` の「GitHub トークン」に貼って「設定する」

### 6.3 保存のされ方（`admin-client.ts`）

| 「このブラウザに保存する」 | 保存場所 | 有効な間 |
|---|---|---|
| オン | localStorage | ブラウザを閉じても残る |
| オフ | sessionStorage | **管理画面にいる間だけ**。管理画面の外のページ（ホームなど）を開くか、タブを閉じると自動で消える |

- トップで1回設定すれば、3つのフォームで共通して使えます。
- **ブラウザ・端末ごと**に保存されます。公開サイトと `localhost` も別扱いです。
- 「消す」ボタンで削除できます。
- トークンはブラウザから GitHub に直接送られるだけで、サイトのサーバーには送りません。

### 6.4 他の人は投稿できるか

できません。`/admin/` は誰でも開けますが、保存には**このリポジトリに書き込み権限がある人のトークン**が必要です。現在、書き込める GitHub アカウントは **Ryouma139 だけ**です。

例外：トークンを保存した端末を他人が使う／トークンが漏れる／共同編集者を追加する。

### 6.5 忘れた・期限が切れたとき

- トークンは後から見直せません。**作り直します。**
- 管理画面用のトークンを開き **Regenerate token**（設定はそのまま、古いトークンは即無効）か、新しく作って古いものを **Delete**。
- ブラウザに保存済みなら、覚えていなくても使えます。
- 保管はパスワード管理アプリへ。メモ帳・チャット・リポジトリには書かない。

### 6.6 push 用の認証（参考）

管理画面のトークンとは別に、PC から `git push` するときの GitHub ログインにも注意があります。**`.github/workflows/` のファイルを変更して push するには、`workflow` の許可が必要**です。

```
gh auth refresh -h github.com -s workflow   # ブラウザで承認し「✓ Authentication complete.」まで待つ
gh auth setup-git                           # git が GitHub CLI のログインを使うようにする
```

`gh auth status` の `Token scopes` に `'workflow'` があれば OK です。

## 7. 公開（GitHub Pages）

| 設定 | 内容 |
|---|---|
| `astro.config.mjs` | `site: 'https://ryouma139.github.io'`、`base: '/kimoti_sekkei'` |
| GitHub Settings → Pages → Source | **GitHub Actions** |
| `.github/workflows/deploy.yml` | `main` への push・毎日 0:00（日本時間、`cron: '0 15 * * *'`）・手動実行 で公開 |

- サイトは `/kimoti_sekkei/` の下に置かれます。**ページ内のリンクは必ず `url()` を通してください**（`/feel/` と直接書くと公開後にリンク切れ）。
- 手元の開発サーバーも `http://localhost:4321/kimoti_sekkei/` で開きます（`/` だけだと 404）。
- `build.yml` は確認用で、push のたびにビルドが2回走ります（問題はありません）。
- **CSS は HTML に埋め込み**（`build.inlineStylesheets: 'always'`）、**ブラウザ用の JS はファイル名にハッシュを付けない**設定にしています（`astro.config.mjs` の `stable-client-file-names`）。
  - 理由：GitHub Pages は HTML を10分キャッシュします。デプロイで CSS・JS のファイル名が変わると、ブラウザに残った古い HTML が消えたファイルを探して 404 になり、**デザインが外れて白い背景にリンクと巨大な顔アイコンだけ**の表示になっていたため。
  - JS は名前が固定なので、デプロイ直後の10分ほどは「古い HTML ＋ 新しい JS」になることがあります。表示が崩れることはありませんが、動きがおかしいときは再読み込みしてください。
